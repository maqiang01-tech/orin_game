## 1. 文档目的

本文档把《异变纪元：幸存者编队》企划需求转换为可编码、可测试、可迁移的技术方案，并与当前 Godot 工程保持一致。它用于约束：

- 模块职责和依赖方向；
- 静态配置、运行态和存档的数据边界；
- 战斗、探索、养成、基地、剧情、轮回和商业化流程；
- 720x1280 竖屏 UI 的场景与组件组织；
- 自动化验证、性能目标和版本发布门槛；
- 从当前原型迁移到后续版本的历史实施设想。

本文档不替代数值平衡表、剧情台本、UI 切图规格或平台合规文档。

## 2. 需求权威与冲突处理

需求发生冲突时，按以下顺序处理：

1. 已确认的五张 720x1280 页面效果图决定视觉构图、层级和页面关系。
2. Production Cut Spec V1.2 决定切图尺寸、透明区、命名和状态族。
3. GDD V3.0 决定玩法目标、内容范围和商业原则。
4. 本技术文档决定实现架构、数据契约和迁移策略。
5. 当前代码是可复用基线，不自动成为最终规则。

### 2.1 已锁定技术决策

| 编号 | 冲突或问题 | 技术决策 |
| --- | --- | --- |

| TD-006 | GDD 承诺不卖数值，但存在经验增幅、资源增益和付费伙伴 | 这些商品在产品审查前保持禁用；技术层只提供商品与权益接口，不默认开放真钱入口。 |

| TD-008 | 中段第 12 章垂直切片仍包含过多伙伴和后期系统 | 该 MVP Demo 实施线已于 2026-09-01 按用户指令取消，prologue 实现已移除。覆盖前的 [完整 V1.0 五人方案](<../.codex/recovery/design-docs/《异变纪元：幸存者编队》MVP Demo设计文档.md>) 与独立的 [V1.1 前三章方案](<../.codex/recovery/design-docs/《异变纪元：幸存者编队》最小MVP Demo设计文档.md>) 仅作非活动归档；后续若恢复开发，需重新确认首发范围。 |

### 4.4 必须优先控制的技术债

1. 不再向 `game_manager.gd` 添加新业务模块。
2. 不再用一张空场景配合数千行脚本动态创建全部 UI。
3. 不允许 UI 直接修改 `PlayerData` 字典字段。
4. 不允许新增 JSON 文件采用新的任意根结构。
5. 不允许在领域逻辑中继续使用全局 `randi()`。
6. 不允许在没有 `save_version` 的情况下发布新存档格式。
7. 不允许旧弹窗战斗和新独立战斗同时成为正式入口。

## 5. 总体架构

### 5.1 分层

```text
Presentation
  Scenes / Pages / Components / ViewModels
            |
            v
Application
  GameFlow / BattleCoordinator / ExplorationCoordinator / Commands
            |
            v
Domain
  Player / Party / Battle / Exploration / Progression / Economy rules
            |
            v
Infrastructure
  DataRegistry / SaveRepository / RNG / Audio / Platform / Commerce adapter
            |
            v
Content
  JSON configs / localization / image and audio assets
```

依赖只能向下。领域层不能引用 Control、Node、Texture、场景路径或平台 SDK。UI 不能直接写存档文件或配置字典。

### 5.2 状态所有权

| 数据类型 | 唯一所有者 | 生命周期 |
| --- | --- | --- |
| 静态定义 | `DataManager`，后续改为 `DataRegistry` | 应用启动到退出，只读 |
| 当前轮状态 | `GameState.run_state` | 新游戏或轮回之间 |
| 永久状态 | `GameState.meta_state` | 跨轮回 |
| 设置 | `SettingsState` | 跨存档 |
| 单场战斗 | `BattleSession` | 进入战斗到结算提交 |
| 单次探索 | `ExplorationSession` | 选择路线到返回基地 |
| UI 临时状态 | 各页面 Controller | 页面显示期间 |

配置对象加载后必须视为只读。创建战斗单位、伙伴实例或奖励时使用深拷贝或显式构造，不得把运行伤害写回 `DataManager`。

### 5.4 自动加载职责

| Autoload | 职责 | 禁止事项 |
| --- | --- | --- |
| `DataManager` | 加载、索引、校验只读配置 | 不保存玩家状态，不生成 UI |
| `GameState` | 持有当前轮和永久状态，提交领域结果 | 不计算复杂战斗规则 |
| `SaveManager` | 原子保存、加载、备份、迁移 | 不决定哪些玩法奖励可得 |
| `SceneManager` | 页面和场景切换 | 不持有页面业务状态 |
| `AudioManager` | BGM/SFX 总线与播放池 | 不由领域层直接依赖 |

不新增万能 `EventBus`。跨页面通知优先使用 Coordinator 的显式 signal，避免全局事件难以追踪。

## 6. 应用生命周期与主流程

### 6.1 启动顺序

```text
启动 Godot
  -> DataManager 读取 JSON
  -> DataValidator 执行结构与引用校验
  -> SaveManager 读取 header 和版本
  -> SaveMigrator 逐版本迁移
  -> GameState 构造 run/meta/settings
  -> MainShell 建立五页导航
  -> 打开上次安全页面，默认 Survival
```

任何关键配置校验失败时，开发构建直接失败；发布构建进入错误页并保留诊断日志，不静默以空字典继续。

### 6.2 核心循环状态机

```text
CAMP_READY
  -> ROUTE_SELECT
  -> EXPLORING
  -> EVENT_RESOLVE | BATTLE_PREPARE
  -> BATTLE_RUNNING
  -> BATTLE_RESULT
  -> EXPLORING | RETURNING
  -> CAMP_READY
  -> TRAINING | TEAM_EDIT | BASE_UPGRADE | STORY
  -> CAMP_READY
```

轮回是独立高层状态：

```text
RUN_ACTIVE -> REINCARNATION_PREVIEW -> REINCARNATION_COMMIT -> NEW_RUN
```

状态切换必须通过应用服务执行。页面按钮只提交 Command，并消费 Result。

### 6.3 统一结果格式

领域命令返回统一结果，不直接弹窗：

```gdscript
{
    "ok": true,
    "code": "route_started",
    "message_key": "explore.route_started",
    "events": [],
    "payload": {},
    "autosave": true
}
```

错误码使用稳定英文 ID，中文仅用于本地化展示。

## 7. 数据驱动规范

### 7.1 配置通用规则

- 文件编码统一 UTF-8 无 BOM。
- ID 使用小写英文 `snake_case`，发布后不可复用或改义。
- 所有引用使用 ID，不使用中文显示名作为键。
- 每个文件包含 `schema_version` 和 `content_version`。
- 新文件统一使用对象根：`metadata`、`entries`。
- 旧数组根和混合对象根通过 Loader Adapter 兼容，逐文件迁移。
- 概率统一使用 0.0 至 1.0。
- 百分比加成统一用小数，例如 15% 写 `0.15`。
- 数值单位写入字段名或 schema，不在同一字段混用整数百分比和小数。
- 所有跨文件引用在启动时检查。

### 7.2 静态定义与运行实例分离

静态伙伴定义不保存等级、当前 HP、装备实例和好感度。运行态只保存变化量和定义引用。

```json
{
  "definition_id": "lin_mei",
  "level": 12,
  "exp": 430,
  "star": 3,
  "current_hp": 328,
  "skill_levels": {"skill_heal": 2},
  "equipment_instance_ids": ["eq_01", "eq_02"],
  "affinity": 162,
  "training_bonus": {"spirit": 8}
}
```

这样修改基础平衡时，不需要重写每个存档中的完整角色配置。

### 7.3 伙伴定义

```json
{
  "id": "lin_mei",
  "name_key": "partner.lin_mei.name",
  "title_key": "partner.lin_mei.title",
  "profession_id": "psychic",
  "rarity_id": "sr",
  "max_level": 30,
  "base_stats": {
    "max_hp": 120,
    "max_energy": 100,
    "attack": 15,
    "defense": 8,
    "spirit": 22,
    "resistance": 12,
    "speed": 10
  },
  "skill_ids": ["skill_basic_shot", "skill_heal"],
  "passive_ids": [],
  "equipment_rules": {
    "weapon_tags": ["light", "focus"],
    "armor_tags": ["light"],
    "accessory_slots": 1
  },
  "recruitment_rule_id": "recruit_lin_mei"
}
```

主角额外保存 `profession_loadout_id`、觉醒节点和专属装备槽。

### 7.4 技能定义

```json
{
  "id": "skill_tactical_assault",
  "name_key": "skill.tactical_assault.name",
  "category": "active",
  "damage_type": "physical",
  "target_rule": "single_enemy",
  "energy_cost": 0,
  "cooldown_rounds": 0,
  "usage_limit": 0,
  "effects": [
    {"op": "damage", "multiplier": 1.2}
  ],
  "ai_tags": ["damage", "single_target"]
}
```

技能效果使用白名单操作，不允许在 JSON 中执行脚本。首批操作：

- `damage`
- `heal`
- `shield`
- `status.apply`
- `status.remove`
- `resource.modify`
- `revive`
- `extra_turn`

### 7.5 异兽定义

```json
{
  "id": "flame_hound",
  "name_key": "beast.flame_hound.name",
  "rank": "elite",
  "affinity_ids": ["fire"],
  "level": 5,
  "base_stats": {
    "max_hp": 180,
    "attack": 25,
    "defense": 10,
    "spirit": 8,
    "resistance": 5,
    "speed": 12
  },
  "skill_ids": ["skill_bite", "skill_flame_burst"],
  "weakness_ids": ["water", "spirit"],
  "drop_table_id": "drops_flame_hound",
  "ai_profile_id": "aggressive_elite"
}
```

掉落表单独配置，避免伙伴碎片和技能书名称直接写入异兽对象。

### 7.6 装备实例

静态装备定义描述槽位、标签和基础属性。玩家背包保存装备实例：

```json
{
  "instance_id": "eq_20260901_0001",
  "definition_id": "weapon_rusty_blade",
  "level": 1,
  "locked": false,
  "affixes": []
}
```

当前 `owned_equipment` 仅保存唯一 ID，无法持有同类多件装备。V0.01 若不做随机词缀，可暂时堆叠数量；进入装备掉落阶段前必须迁移为实例模型。

### 7.7 探索节点与效果

```json
{
  "id": "route_1_1_node_1",
  "type": "search",
  "text_key": "route.route_1_1.node_1",
  "conditions": [
    {"op": "resource.gte", "id": "food", "value": 1}
  ],
  "effects": [
    {"op": "resource.add", "id": "food", "value": 8},
    {"op": "resource.add_chance", "id": "medicine", "value": 2, "chance": 0.5}
  ],
  "next": "route_1_1_node_2"
}
```

效果使用有序数组，避免 Dictionary 无法表达重复操作和稳定顺序。旧 `effects` Dictionary 由兼容层转换。

### 7.8 全量数据校验

启动和 CI 必须校验：

- JSON 可解析、根结构和 schema 版本合法；
- ID 唯一且符合命名规则；
- 技能、异兽、伙伴、装备、路线、掉落、剧情引用存在；
- 概率范围合法且奖池权重可归一化；
- 数值非负、上限大于初始值；
- 每个伙伴至少有基础攻击；
- Boss 和结局条件可达；
- 资源 ID 存在于资源注册表；
- 图片、音频和场景路径可加载；
- 状态族和按钮状态完整。

当前 `validate_data.gd` 只覆盖少量字段，应扩展为独立 headless 验证入口并返回非零退出码。

## 8. 玩家、队伍与成长

### 8.1 玩家状态拆分

`PlayerData` 拆为以下聚合：

| 聚合 | 内容 |
| --- | --- |
| `RunState` | 天数、时段、生存值、当前章节、资源、路线、当前队伍 |
| `RosterState` | 已拥有伙伴和伙伴实例状态 |
| `InventoryState` | 资源、消耗品、装备实例、技能书 |
| `BaseState` | 基地等级和设施等级 |
| `StoryState` | 当前步骤、旗标、已完成章节、结局进度 |
| `MetaState` | 轮回次数、永久天赋、Boss 情报、历史最佳记录 |

`PlayerData` 在迁移期可作为 facade，但不继续承载所有规则实现。

### 8.2 队伍状态：完整版五人，MVP 单人

最小 MVP 的 `member_ids` 固定为 `["player_chenmo"]`，不初始化阵型格或组合技。以下五席规则是第 5 章引入伙伴系统后的完整版本目标，不是前三章发布门槛。

```gdscript
class_name PartyState

var member_ids: Array[String]       # 标准 5 人，最多 5 人
var formation_grid: Array[String]   # 9 格，空位为 ""
var formation_id: String
```

约束：

- 主角不能被移出标准队伍；教程或明确的剧情编队例外由关卡配置声明；
- 同一伙伴不能重复出现在 `member_ids` 或多个阵型格；
- 每名成员必须占用一个唯一的 3x3 阵型格，未上阵成员不得残留在阵型中；
- 标准探索和战斗以 5 人开始，底层规则允许教程、剧情减员或伙伴阵亡后的 1 至 4 人队伍；
- 战斗开始时所有未失能成员进入初始行动顺序，不存在替补队列；
- 队伍全灭仅在全部参战成员失能时成立；
- 阵型加成和组合技条件按五名参战成员及其站位统一计算。

### 8.3 等级与经验

- 等级上限由伙伴定义提供，默认 30；
- 升级经验曲线放入 `level_curve.json`；
- 属性成长使用定义中的成长曲线，不用随机 `+2~3` 直接写存档；
- 若保留随机成长，随机结果必须由运行种子生成并持久化；
- 技能点在升级事务中与等级同时提交，避免中途保存造成丢失。

### 8.4 星级、技能和好感度

升级事务统一按“校验、扣除、应用、发事件、保存”执行：

```text
validate request
  -> verify definition and cap
  -> verify resource balance
  -> deduct resources
  -> mutate one aggregate
  -> emit progression event
  -> autosave
```

好感度阈值、星级成本、技能升级成本移入配置。UI 不使用数组索引作为永久技能身份，统一使用 `skill_id`。

### 8.5 主角觉醒

觉醒条件通过领域事件计数，不由 UI 判断：

- `battle.lethal_damage_survived`
- `exploration.relic_found`
- `battle.beast_defeated`
- `battle.won_low_hp`
- `battle.boss_defeated`
- `affinity.level_reached`
- `collection.relic_set_completed`
- `partner.level_reached`

`AwakeningService` 消费事件，检查未解锁节点，产出 `talent_unlocked` 结果。每个事件必须幂等，避免重复加载或重放导致二次解锁。

### 8.6 属性训练

训练命令包含 `partner_id`、`training_id` 和当前时段。事务同时验证并扣除口粮、药品和时段。训练结果写入 `training_bonus`，不直接修改静态基础属性。

## 9. 战斗系统

### 9.1 目标

- 规则与 UI 解耦；
- 同一输入和种子产生同一结果；
- 支持最多 5 名玩家单位同时参战；
- 支持手动、半自动和全自动；
- 支持普通、精英、Boss、剧情战斗；
- 所有动作产出结构化事件供日志、动画、音效和测试使用。

最小 MVP 只启用手动、单人、普通剧情战斗。半自动、全自动、精英、Boss 和五人表现均延后，但底层数据结构不得把人数硬编码为 1。

### 9.2 BattleState

```gdscript
{
    "battle_id": "battle_uuid",
    "rules_version": 1,
    "seed": 123456,
    "round": 1,
    "phase": "await_action",
    "units": {},
    "player_unit_ids": [],
    "enemy_unit_ids": [],
    "turn_order": [],
    "turn_index": 0,
    "events": [],
    "result": {}
}
```

运行代码最终使用 typed `BattleState` 和 `UnitState`。迁移期可在序列化边界保留 Dictionary。

### 9.3 回合阶段

```text
SETUP
  -> ROUND_START
  -> TURN_START
  -> AWAIT_ACTION
  -> VALIDATE_ACTION
  -> RESOLVE_ACTION
  -> TURN_END
  -> NEXT_UNIT
  -> ROUND_END
  -> CHECK_END
  -> ROUND_START | SETTLEMENT
```

每个阶段只允许有限状态变化，避免 UI 连点和异步动画重复提交动作。

### 9.4 行动命令

```gdscript
{
    "actor_id": "lin_mei",
    "type": "skill",
    "skill_id": "skill_heal",
    "target_ids": ["player_chenmo"],
    "item_instance_id": ""
}
```

支持动作：`attack`、`skill`、`guard`、`item`。所有动作都要校验当前 actor、目标、能量、冷却、使用次数和状态限制。V0.01 不提供战斗中换人；阵型调整只在战斗外完成。

### 9.5 命中、暴击与伤害

V0.01 规则参数：

```text
attack_value = physical ? ATK : SPI
defense_value = physical ? DEF : RES
mitigation = defense_scale / (defense_scale + defense_value)
base_damage = attack_value * skill_multiplier * mitigation
damage = base_damage * affinity * critical * guard * position * modifiers
final_damage = max(minimum_damage, round(damage))
```

所有系数来自 `balance_rules.json`：

```json
{
  "schema_version": 1,
  "combat_rules_version": 1,
  "defense_scale": 100.0,
  "minimum_damage": 1,
  "base_crit_rate": 0.05,
  "crit_per_speed": 0.003,
  "crit_multiplier": 1.8,
  "base_hit_rate": 0.95,
  "minimum_hit_rate": 0.70,
  "dodge_per_speed": 0.0008,
  "weakness_multiplier": 1.30,
  "guard_damage_multiplier": 0.50,
  "round_energy_regen": 0.20
}
```

当前代码没有完整闪避结算，V0.01 必须在伤害前加入命中检查。UI 展示的预计伤害只能使用区间，不提前消耗随机数。

### 9.6 行动顺序

- 每回合开始根据最终速度重建；
- 同速时玩家单位优先，再按站位索引，最后按稳定 ID；
- 加速、减速和冰冻在下一次排序生效；
- 额外行动作为显式 `extra_turn` 事件插入，不重复构建整轮；
- 复活单位从下一轮进入行动顺序，除非技能明确写即时行动。

### 9.7 状态效果

统一状态实例：

```gdscript
{
    "status_id": "burn",
    "source_unit_id": "enemy_flame_hound_0",
    "remaining_rounds": 3,
    "stacks": 1,
    "value": 0.05,
    "tags": ["debuff", "dot", "fire"]
}
```

必须定义叠加规则：`replace`、`refresh`、`stack`、`independent`。护盾有独立剩余值。状态结算顺序固定并写测试。

### 9.8 AI

AI 使用 `ai_profile` 配置评分，不在代码中为每只异兽写分支。基础评分考虑：

- 生存阈值；
- 技能可用性；
- 目标弱点；
- 击杀可能性；
- 群体技能收益；
- 治疗和护盾缺口；
- Boss 阶段和脚本化行为。

相同 BattleState 与种子应产生相同 AI 决策。

### 9.9 战斗奖励

奖励由 `RewardService` 计算，结算页只展示。提交必须幂等：`battle_id` 已提交时不能重复发奖。固定奖励、掉落表、首杀、任务奖励分别记录来源。

### 9.10 战斗事件

核心事件：

- `round_started`
- `turn_started`
- `action_committed`
- `damage_applied`
- `healing_applied`
- `status_applied`
- `unit_defeated`
- `battle_finished`
- `rewards_granted`

战斗 UI 根据事件播放轻量 Tween、飘字、音效和日志，不反向控制规则。

## 10. 探索、时间与生存

### 10.1 时间模型

```gdscript
enum TimeSlot { MORNING, AFTERNOON, NIGHT }
```

每天三个时段。消耗时段后：

1. 推进 `time_slot`；
2. 跨日时增加 `day`；
3. 结算饥饿、水分、感染、天气和世界事件；
4. 根据章节配置更新可用内容；
5. 触发自动存档。

不再在 `PlayerData` 中硬编码每 4 天一章。

### 10.2 探索会话

`ExplorationSession` 保存：

- `route_id`
- `seed`
- `current_node_id`
- `visited_node_ids`
- `resolved_choice_ids`
- `pending_battle`
- `collected_rewards`
- `status`

进入节点、选择分支、战斗返回和撤离都通过 Session 执行。应用崩溃后可从最后安全节点恢复，不能重复领取已结算节点奖励。

### 10.3 节点类型

- `battle`
- `search`
- `recruit`
- `story`
- `merchant`
- `boss`
- `branch`
- `rest`
- `exit`

地牢网格属于探索的一种 Route Provider。`DungeonManager` 负责生成地图，统一转换为 ExplorationSession 可消费的节点，不另建一套奖励和战斗提交逻辑。

### 10.4 条件与效果语言

条件和效果只允许注册过的操作。条件示例：

- 资源数量；
- 伙伴拥有与好感度；
- 章节、天数、时段；
- Boss 击败状态；
- 旗标存在；
- 属性阈值；
- 主角觉醒节点。

每次随机判定记录 `roll_id` 和结果，以便存档恢复和问题复现。

### 10.5 生存值

HP、体力、饥饿、水分、感染各自有 0 至上限范围。数值变化通过 `SurvivalService`，并统一产出阈值事件，例如：

- `hunger_low`
- `dehydrated`
- `stamina_exhausted`
- `infection_critical`

负面效果由配置决定，UI 只显示状态。

## 11. 资源、背包与经济

### 11.1 资源注册表

每个资源包含 ID、显示名、默认上限、是否可付费、溢出规则和图标。GDD 核心资源映射为：

| 企划资源 | 技术 ID |
| --- | --- |
| 口粮 | `food` |
| 药品 | `medicine` |
| 晶核 | `cores` |
| 记忆碎片 | `memory_shards` 或伙伴专属 fragment ID |
| 补给券 | `tickets` |

当前额外资源如 `spirit_battery`、`ammo`、`rare_material`、`spirit_core`、`gold`、`crystal` 必须在注册表中定义用途和来源。

### 11.2 资源事务

`ResourceService.add()` 返回：

```gdscript
{
    "accepted": 20,
    "overflow": 5,
    "converted": {"camp_contribution": 5}
}
```

当前 `add_resource()` 会静默截断上限，与企划的“转化为营地贡献”不一致，必须修正。

### 11.3 抽奖

本地原型可用固定种子模拟，但不可作为真实付费实现。抽奖服务必须记录：

- 池版本；
- 抽取序号；
- 保底计数；
- 奖励 ID；
- 重复伙伴转化；
- 事务 ID；
- 发奖提交状态。

十连和五十抽保底必须通过自动测试覆盖边界值。

### 11.4 商业模式技术边界

推荐单人开发首发采用离线买断，不接充值抽奖。若选择联网 F2P，至少需要：

- 平台登录或匿名账号；
- 服务端时间；
- 收据校验；
- 服务端商品目录和奖池版本；
- 服务端抽奖与幂等发奖；
- 订单补单；
- 隐私、未成年人、概率公示和地区合规审查；
- 客服查询和审计日志。

客户端只依赖 `CommerceProvider` 接口：

```gdscript
purchase(product_id: String) -> PurchaseResult
restore_purchases() -> Array[Entitlement]
query_products() -> Array[Product]
```

V0.01 使用 `DisabledCommerceProvider`，所有真钱按钮隐藏。

## 12. 基地、图鉴、剧情与结局

### 12.1 基地

设施定义迁移到 `base_facilities.json`：工作台、仓库、床铺、医疗台、厨房、发电机。配置包含等级上限、成本曲线、前置设施和效果。升级由 `BaseService` 执行，设施等级不能超过基地等级。

### 12.2 图鉴

图鉴只保存发现状态和计数，不复制完整定义：

```gdscript
{
    "beast_id": "flame_hound",
    "seen": true,
    "defeated_count": 4,
    "intel_ids": ["weakness"],
    "completed": false
}
```

图鉴奖励由一次性 claim ID 保证幂等。

### 12.3 主线与剧情

剧情执行器支持白名单步骤：

- `dialogue`
- `narration`
- `choice`
- `set_flag`
- `grant_reward`
- `start_battle`
- `unlock_route`
- `unlock_partner`
- `chapter_complete`

剧情步骤只引用本地化键和资源 ID。跳过剧情仍必须执行必要的状态效果，但不能重复发奖。

### 12.4 结局

五种结局通过条件表达式配置。结局判定顺序明确，若多个条件同时满足，按优先级展示主结局，其余记录为已达成。队伍全灭不应直接永久删除存档，先进入结算和确认流程。

### 12.5 轮回

轮回提交分两步：预览和确认。预览是纯计算，确认时：

1. 计算评价、印记和天赋点；
2. 写入永久状态；
3. 保存永久存档；
4. 创建新的当前轮状态；
5. 保存当前轮存档；
6. 进入新轮首页。

任一步失败都不能留下“永久奖励已发但当前轮未重置”的半完成状态。

## 13. UI 技术方案

### 13.1 视觉基线

- 设计画布：720x1280；
- 五张确认效果图是页面构图权威；
- 风格：末日废土、黑金、暗色、磨损金属、橙金选中态；

现有 `docs/UI布局与交互汇总.md` 继续作为交互细则，资源审核结果见 `.codex/assets/runs/baseline-20260901/CURATION_REPORT.md`。

`MainShell` 只负责：

- 五页容器；

- 全局弹窗层；

页面 ID 统一：

```text

explore
team
base
reincarnation
```

历史 `camp/story/inventory` 只在迁移映射中存在，不能继续作为新页面 ID。

### 13.3 场景组件化

最小公共组件：

- `TopStatusBar`
- `BottomNavigation`
- `ImageStateButton`
- `ResourceCounter`
- `PartnerCard`
- `FormationCell`
- `BattleUnitCard`
- `HpBar`
- `EnergyBar`
- `StatusChipRow`
- `RewardRow`
- `ConfirmDialog`
- `ToastLayer`

组件对外暴露 signal 和 `bind(view_data)`，不读取 `GameState` 单例。

### 13.4 页面 Controller

每个页面由独立脚本负责绑定和命令转发：

```text
TeamPage
  -> TeamViewModel.from_state()
  -> render cards and formation
  -> emit place_requested(partner_id, slot)

```

UI 刷新采用局部更新，不在每次按钮点击后重建全部页面树。

### 13.5 自适应与输入

- 以 720x1280 设计区域等比缩放；
- 宽屏保留左右留白，不横向拉伸；
- 移动端读取安全区，顶部和底部控件不得进入刘海或手势区域；
- 最小触控目标 44 逻辑像素；
- 键鼠、键盘焦点和触控均可完成核心闭环；
- hover 不承担唯一信息；
- normal、hover、focus、pressed、disabled、selected 状态不得改变控件尺寸；
- 动态文字必须限制行数、换行或滚动，不能遮挡邻近控件。

### 13.6 战斗 UI

正式入口只保留 `BattleScene`。旧主界面战斗弹窗在功能对齐后删除入口。战斗 UI 消费 BattleEvent 队列，动画期间锁定命令提交，动画跳过不影响规则结果。

## 14. 存档系统

### 14.1 文件

```text
user://save/run_slot_0.json
user://save/meta.json
user://save/settings.json
user://save/run_slot_0.bak.json
```

### 14.2 Header

每个存档包含：

```json
{
  "save_version": 3,
  "content_version": "0.01.0",
  "build_version": "0.01.0-dev.42",
  "saved_at_utc": "2026-09-01T00:00:00Z",
  "profile_id": "local_0",
  "payload": {},
  "checksum": "sha256"
}
```

校验和用于发现损坏，不作为反作弊安全机制。

### 14.3 原子写入

```text
serialize
  -> write .tmp
  -> flush and close
  -> parse .tmp for verification
  -> rotate current to .bak
  -> rename .tmp to current
```

加载顺序：当前文件、备份文件、默认新档。发生恢复时在 UI 中明确提示，不静默覆盖损坏文件。

### 14.4 迁移

```gdscript
migrate_v1_to_v2(data)
migrate_v2_to_v3(data)
```

迁移必须逐版本执行、幂等并有 fixture 测试。当前无版本的旧存档视为 V1。迁移前保留原始副本。

### 14.5 自动保存点

- 探索开始和安全节点结算后；
- 战斗结算提交后；
- 培养、装备、基地升级成功后；
- 商店事务成功后；
- 章节完成后；
- 轮回确认事务完成后；
- 应用进入后台时。

战斗动作中间不写主存档，除非实现完整 BattleSession 恢复。

## 15. 随机数、日志与可复现性

### 15.1 随机种子

每一轮保存 `run_seed`。探索路线、节点判定、战斗和掉落通过稳定子种子派生：

```text
hash(run_seed, system_id, content_id, sequence_number)
```

禁止领域代码调用全局 `randi()` 或 `randf()`。使用注入的 `RandomNumberGenerator`。

### 15.2 结构化日志

开发日志至少包含：

- build 和内容版本；
- command 名称；
- battle/route/transaction ID；
- seed；
- 稳定错误码；
- 数据校验失败路径；
- 存档迁移步骤。

## 16. 测试与验收

### 16.1 测试层级

| 层级 | 内容 | 运行方式 |
| --- | --- | --- |
| 数据校验 | JSON、引用、概率、资源路径 | 每次提交、Godot headless |
| 领域单元测试 | 公式、状态、成长、资源、条件 | 每次提交 |
| 集成测试 | 探索到战斗到结算到存档 | 每次合并 |
| UI 交互测试 | MVP 章节热点、背包、地图、战斗、结算；后续再覆盖五页导航 | 每次 UI 变更 |

### 16.2 战斗必测用例

MVP 发布门槛：

- 陈末单人每轮只行动一次；
- 1 对 1 和 1 对 3 行动顺序稳定；
- 多目标切换只攻击当前合法目标；
- 防御使下一次直接伤害按配置减半；
- 最低伤害、命中和暴击边界；
- 变异蟑螂物理减伤 30%、火焰倍率 150%；
- 医疗包不会超过最大 HP；
- 燃烧弹材料在失败重试时正确回滚；
- 全灭、胜利、奖励幂等和同种子重放一致。

完整版本回归门槛在五人功能进入开发后增加：五人行动序列、阵型、护盾、状态叠加、DOT、复活、额外行动和团队技能。它们不阻塞最小 MVP。

### 16.3 经济必测用例

- 资源不足不扣除；
- 多资源事务全成或全败；
- 上限溢出转营地贡献；
- 重复伙伴转碎片；
- 10 抽和 50 抽保底边界；
- 重复提交事务不重复发奖；
- 存档回滚不复制商品。

### 16.5 完成定义

一个功能只有同时满足以下条件才算完成：

- 配置 schema 和引用校验通过；
- 领域逻辑不依赖 UI；
- 成功、失败和边界测试存在；
- 存档字段和迁移已定义；
- UI 支持 720x1280、桌面缩放和触控安全区；
- 正常、按下、禁用和选中状态完整；
- 自动保存点正确；
- headless 项目启动无错误；
- 没有新增未登记的资源路径。
